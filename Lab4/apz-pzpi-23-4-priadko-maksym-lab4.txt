2 ЗАВДАННЯ
В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір:
- масштабувати сервер горизонтально — багато копій сервера виконують однакові функції для різних користувачів;
- масштабувати сервер вертикально — різні мікросервіси виконують різні функції і масштабуються окремо одне від одного. 
З технічної точки зору, масштабування можна виконати так:
- деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів;
- деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати.
- ваш власний спосіб показати що система може масштабуватись.


3 ОПИС ВИКОНАНОЇ РОБОТИ

3.1 Стратегія масштабування системи
     Для системи обрано горизонтальне масштабування backend API. Суть стратегії полягає в тому, що замість збільшення ресурсів одного сервера створюється декілька однакових екземплярів API. Кожен pod виконує однакову бізнес-логіку та може обробляти HTTP-запити користувачів.
     Kubernetes Service виконує роль внутрішнього балансувальника навантаження: він має один стабільний endpoint, а реальні запити спрямовуються на доступні pod-и backend API. Завдяки цьому клієнт не знає, який саме pod обробив запит, а кількість pod-ів можна змінювати без зміни адреси сервісу.
     База даних у цій роботі залишається однією, оскільки її горизонтальне масштабування потребує окремих механізмів реплікації, шардингу або керованого кластерного рішення. Такий підхід дозволяє сфокусуватися саме на масштабуванні stateless backend-рівня.
– рівень API масштабується горизонтально за кількістю replicas у Kubernetes Deployment;
– Kubernetes Service розподіляє HTTP-запити між pod-ами API;
– SQL Server винесений в окремий сервіс і має постійне сховище;
– кількість replicas можна змінювати вручну через dashboard або команду kubectl scale;
– навантажувальне тестування виконується окремим PowerShell-скриптом.

3.3 Аналіз вузьких місць системи
     При горизонтальному масштабуванні backend API кількість оброблюваних HTTP-запитів може зростати майже пропорційно кількості replicas лише для тих операцій, які не обмежуються спільним станом. У системі PythonWiki таким спільним ресурсом є база даних SQL Server, тому саме вона може стати головним вузьким місцем при збільшенні навантаження.
Основні потенційні вузькі місця наведено в таблиці 3.2.
РесурсЯк проявляється проблемаЩо вичерпується першимМожливе рішенняCPU pod-ів APIЗростає час обробки запитів, збільшується latencyПроцесорні ресурси контейнерів APIЗбільшення replicas або CPU limitsSQL ServerПовільні SELECT/INSERT/UPDATE, черги підключеньCPU, RAM, дисковий I/O, connection poolОптимізація запитів, індекси, кешування, окремий managed DBДискове сховище DBПовільний запис і читання данихIOPS та пропускна здатність дискаШвидше сховище, оптимізація транзакційМережа та ServiceЗбільшення часу відповіді при великій кількості запитівПропускна здатність мережі та overhead балансуванняОптимізація payload, gzip, кешуванняОдин локальний Kubernetes nodeУсі pod-и працюють на одному Docker Desktop вузліCPU/RAM локального комп’ютераРеальний кластер з кількома node-ами
     Для статичних або легких endpoint-ів, наприклад Swagger, першим обмеженням найчастіше стає CPU API або ресурси локального Docker Desktop. Для endpoint-ів, які активно працюють із даними, першим вузьким місцем буде SQL Server, оскільки всі replicas API звертаються до однієї бази даних.
3.5 Опис навантажувального тестування
     Для перевірки впливу масштабування на витримуване навантаження підготовлено PowerShell-скрипт loadtest/Invoke-LoadTest.ps1. Тест виконує паралельні HTTP-запити до вказаного URL та рахує кількість успішних запитів, помилок, загальну тривалість, кількість запитів за секунду, середню затримку, p95 та p99.
     Тестування виконується за таким сценарієм:
– розгорнути систему через install.bat;
– у dashboard встановити кількість replicas = 1;
– запустити load test для http://localhost:8080/swagger;
– повторити тест для replicas = 2 та replicas = 3;
– порівняти RPS та latency для різної кількості pod-ів.
     Таблиця 3.3 призначена для внесення фактичних результатів після запуску тестів на локальному комп’ютері. Значення RPS залежать від характеристик ПК, стану Docker Desktop, endpoint-а та кількості фонових процесів, тому їх потрібно отримати безпосередньо під час демонстрації.

Якщо тестувати endpoint-и, які активно використовують базу даних, приріст RPS буде меншим через обмеження одного SQL Server.
